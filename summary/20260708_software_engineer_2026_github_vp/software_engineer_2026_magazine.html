2026，還該成為軟體工程師嗎？

Scott Hanselman 的答案並不浪漫：AI 讓寫 code 更容易，也讓粗糙的工程更容易泛濫。真正值得投入的，不是「會不會被取代」，而是你是否願意學會負責、設計、溝通，並把軟體真的交到世界上。

每個年代都宣布過 coding 已死

Hanselman 從 1984 年開始寫程式。他說自己已經看過幾十年的恐慌：高階語言會殺死程式設計，IntelliSense 會讓人變笨，Stack Overflow 讓大家只會複製貼上。現在輪到 AI。這不是第一次，也不會是最後一次。

他的姿態不是否認變化，而是把變化放回工具史。彩色螢幕、IDE、自動完成、雲端、行動裝置，每一次都改變工程師的工作面貌，但沒有讓 craft 消失。AI 也是 power tool。它能讓工程師更快抵達某些結果，也能更快製造一堆看似可用、實際上缺乏架構的 code。

所以問題不再是「AI 會不會寫 code」。它已經會。真正的問題是：當 code 變得便宜，誰來負責判斷它是否應該存在、如何演進、如何測試、如何交付、出了事誰承擔？

AI 不會自動生成 architecture。它會討好你、完成 feature，也可能把系統推向巨大的混亂物件。

AI 時代，責任沒有外包

Hanselman 用一個很直接的比喻說明責任：如果一個陌生人在網路上送來 PR，你沒有看就 merge，結果傷害使用者，那不是陌生人的錯，是你的錯。AI 也是一樣。它會犯錯，人也會犯錯，但產品責任仍在點下 merge 的人身上。

這也是他不把 AI workflow 當成即興 vibe 的原因。他談到 code signing、testing、Dependabot、agentic workflow、review pipeline。換句話說，AI 不是讓 SDLC 消失，而是讓好的 SDLC 更重要。當產出速度提高，沒有閘門的團隊只會更快把不可信的東西送到使用者面前。

對 SWE 來說，這是 2026 的第一個分水嶺：會使用 AI 工具不稀奇；能把 AI 產出放進工程紀律裡，才是職業能力。

不要把 junior 斷掉

訪談裡最有組織層級重量的一句話，是 Hanselman 對早期工程師的擔憂：如果不繼續雇用、培養 early-career developers，未來的 senior 從哪裡來？這不是情懷問題，而是供應鏈問題。軟體組織不能只採收成熟工程師，卻停止栽培新人。

他借用護理領域的 preceptor 概念：不要把新人放在「低一等」的位置，然後期待他自己從缺乏 context 的坑裡爬出來。更健康的設計，是把 senior 的工作明確定義為製造更多 senior。這也意味著 AI 教學工具應該因人而異：junior 和 senior 不該用同一種模型互動方式。

AI 可以成為學習加速器，但它也可能讓初學者跳過痛苦卻必要的理解過程。好的工具應該讓人停下來解釋、自己寫一部分、接受小測驗、補齊 mental model，而不是把所有過程都變成一鍵完成。

基本功不是懷舊，是壓力測試

當被問到如果回到 20 歲、想成為真正的工程師該做什麼，Hanselman 的答案很樸素：基本功，以及溝通與清晰度。程式設計本來就是把意圖表達到足夠清楚，讓它能 compile、run、test。AI 只是把這件事推到另一個介面：你的 prompt、你的需求拆解、你的 review 意見，也是在寫程式。

因此，真正值得練的不是背更多工具名，而是把模糊想法變清楚的能力。你能不能看著另一個人解釋你的 trade-off？能不能在白板上邊想邊說？能不能承認不知道，然後把問題拆到可以求證？這些能力在 AI 時代沒有過時，反而變成辨識工程師深度的方式。

他的 rapid-fire 回答也很有意思：該讀 computer science 還是 AI？他說該讀 software engineering，因為那是把東西 ship 出去的部分。這句話對 SWE 尤其重要。演算法與模型當然重要，但職涯本身多半是在與需求、legacy、測試、部署、使用者、文件、團隊溝通一起工作。

另一個更尖銳的回答是「每個人都該學哪一種語言？」Hanselman 說的是 English，並立刻承認這很不理想。這不是把英文包裝成能力優越感，而是在描述眼前的工作現實：大量文件、issue、prompt、開源討論、跨國協作與 AI 工具介面仍高度依賴英文。對非英語母語的 SWE 來說，這是一個不公平但值得正視的槓桿。

作品集要真，不要只像

許多 junior 會拿 clone project 當作品集。Hanselman 不否定 tic-tac-toe 或 Minecraft clone 的練習價值，但他指出問題：如果你只是利用某個巨大名詞的既有語意，AI 能很快補出表面相似的東西；但當你不能說出那個產品名，必須自己描述規格時，需求的重量就浮現了。

他的建議是做「你真的在乎」的東西。Tiny Tool Town 那種小工具集合，看起來輕鬆甚至有點荒唐，但背後有 license、CI/CD、release、issue triage、維護規則。它不是履歷上的裝飾品，而是會被照顧的軟體。

對求職者來說，這比完美複製熱門產品更有信號。因為真實小產品會暴露你的品味：你怎麼處理 scope？怎麼維護？怎麼寫 README？怎麼讓它部署？怎麼判斷什麼可以 stale、什麼需要修？這些比「AI 幫我生成了一個 clone」更接近工程現場。

簡單架構，仍然是高手的語言

訪談後段，Hanselman 展示自己的工具與網站時，順手講了一段架構哲學：很多人太愛用資料庫，但有些東西根本不需要。GitHub issues 可以是資料庫；Astro 產生的 static site 可以放 CDN；部落格二十多年內容也可能只是幾百 MB 的 XML，整包進記憶體、只在新增文章時 invalidate cache。

這段不是反資料庫，而是反射性過度設計。SWE 的成熟度，在於知道什麼問題需要 real-time、Postgres、queue、distributed system；也知道什麼問題其實每小時更新一次就好，cache 就夠，static 就夠。

所以，2026 年還該成為 SWE 嗎？如果你期待這份工作只剩下輸入 prompt、收割程式，那答案可能是否定的。但如果你想學會把問題變成產品、把工具放進紀律、把新人帶成高手、把小作品維護成真正的系統，那答案反而更清楚：值得，而且門檻變得更真實。

Ask Before Merge

  1. 這段 code 的意圖是否能被下一個人看懂？
  2. 測試是否覆蓋 AI 最可能胡說的地方？
  3. 如果它壞了，誰會受影響，誰負責回復？
  4. 這是必要架構，還是被工具速度煽動出的複雜度？

Career Bet

把 AI 當成放大器，而不是替身。它會放大你的基本功，也會放大你的混亂。職涯策略不是避開 AI，而是讓自己成為能指揮、驗證、約束它的人。

工程師的未來，不是更少人寫 code，而是更少人能逃避判斷。

這支訪談的價值，在於它沒有把 AI 包裝成末日或樂園。它提醒 SWE：工具變強以後，職業倫理、架構感、溝通力與維護責任反而更清楚地浮出水面。

如果你正在決定是否進入這一行，真正該問的不是「AI 會不會取代我」，而是「我是否願意成為那個對系統、使用者與下一代工程師負責的人」。
